IWhat it is

A math coprocessor that gets the same answer everywhere (cft-fp256 19de866 README.md:3). It does IEEE 754 arithmetic at four precisions - 32, 64, 128 and 256 bits - and guarantees that the same inputs give the same bits whether the work runs on a laptop CPU, in a browser tab, on a microcontroller, or on the FPGA card it was designed for (cft-fp256 19de866 README.md:5).

IIWhat it is not

Raw fp32 and fp64 throughput (cft-fp256 19de866 README.md:67). Every CPU and GPU on the market serves those formats at clocks and lane counts an FPGA fabric will not match, and nothing here pretends otherwise (cft-fp256 19de866 README.md:67). The tile earns its place at the precisions commodity hardware does not offer, and on the guarantee that the answer does not move (cft-fp256 19de866 README.md:73).

IIIThe contract

Named levels, quoted from CONFORMANCE.md: “Level A - IEEE 754-2019 in radix 2 (cft-fp256 19de866 CONFORMANCE.md:17)” is the standard itself; “Level B - the cft-fp256 profile (cft-fp256 19de866 CONFORMANCE.md:23)” is “Level A, plus every choice the standard leaves to the implementation fixed to one answer, plus operations the standard does not define (cft-fp256 19de866 CONFORMANCE.md:23).” The relationship runs one way, in the document's own words: “An implementation conforming to the cft-fp256 profile conforms to (cft-fp256 19de866 CONFORMANCE.md:28) IEEE 754-2019 in radix 2 for the operations the profile covers (cft-fp256 19de866 CONFORMANCE.md:29).”

The README states the promise directly: “That guarantee is the product (cft-fp256 19de866 README.md:10).” The hardware only makes it faster (cft-fp256 19de866 README.md:10).

The contract is versioned. CONFORMANCE.md opens with its profile, “Profile 3.1, 2026-10-13 (cft-fp256 19de866 CONFORMANCE.md:3)” (profile 3 was 2026-10-05, profile 2 2026-10-02 and profile 1 2026-09-16 (cft-fp256 19de866 CONFORMANCE.md:3)), and says of the tree: “a minor step: cases added, none moved (cft-fp256 19de866 CONFORMANCE.md:338).” A minor step is “an addition that changes no recorded case and no accepted image (cft-fp256 19de866 CONFORMANCE.md:284).”

What CONFORMANCE.md says of the tree, “a minor step: cases added, none moved (cft-fp256 19de866 CONFORMANCE.md:338),” is that document's own word as of its last change, 2026-10-15 (cft-fp256 19de866 git log -- CONFORMANCE.md). The ledger's newest entry, of 2026-10-30 (cft-fp256 19de866 docs/VALIDATION.md:26149), reports a fix that changed published records: “The 8 that change are the rtz and rdn transcendental sets of each format, each by exactly one record, exp2m1(emax + 1): the same value, flags 20 to 16. The unfixed model's 72 rtz and rdn sets equal the committed record, so those 8 records are the published ones moving (cft-fp256 19de866 docs/VALIDATION.md:26179).” The same document calls a change to any recorded bit or flag a major step: “a change to any recorded bit or flag, or to an accepted image's result, flags, STATUS or acceptance (cft-fp256 19de866 CONFORMANCE.md:281).” The pin holds both.

VKept failures

  • cocotb's inability to set an exit code — stated in its own makefile at Makefile.inc:88, which checks only that the file *exists* — meant three real RTL failures were reported as a pass (cft-fp256 19de866 CLAUDE.md:116). Fixed by the entry 2026-09-12 - two gates that could not fail, and the path that has always been the critical one (cft-fp256 19de866 docs/VALIDATION.md:10955), commit f192bf0 (cft-fp256 f192bf0).
  • exp2 at x = emin - p (cft-fp256 19de866 CONFORMANCE.md:394): Its exact value 2^(emin - p) is half the smallest subnormal, the tie between +0 and it, which IEEE 754's roundTiesToAway (rmm) rounds to the subnormal. The model rounded it as a quarter of the subnormal and gave +0 (cft-fp256 19de866 CONFORMANCE.md:394). Step 6's design study M1 found it (its question 5), verifier-VM1 confirmed it (cft-fp256 19de866 CONFORMANCE.md:402) — in the entry 2026-10-05 - the golden model's exp2 tie fixed, and the conformance profile's major step to 3 (parcel XT); M1's design study merged as a design record (cft-fp256 19de866 docs/VALIDATION.md:18206). Fixed by commit ca43695 (cft-fp256 ca43695).
  • At x = emax + 1, under roundTowardZero and roundTowardNegative, exp2m1 returned the largest finite, which is right, with overflow | inexact (0x14), which is wrong (cft-fp256 19de866 docs/VALIDATION.md:26152). Reported, in the entry's words, “from a clean-room audit of loganw234/muse-softfloat (binary16/32/64), cross-tested against this library and an exact arbiter (cft-fp256 19de866 docs/VALIDATION.md:26151)” — in the entry of 2026-10-30 (cft-fp256 19de866 docs/VALIDATION.md:26149). No gate had caught it: “The MPFR oracle never asked (cft-fp256 19de866 docs/VALIDATION.md:26168).” Fixed by commit 48e2aa22 (cft-fp256 48e2aa22).

The record's newest timing of the golden stage is one run on one machine: the runner's stage, which runs “PY -m pytest "$ROOT/python/tests" -q -rs --color=no (cft-fp256 19de866 verify/run.sh:639)” and names no worker option, took “golden ok 3,385 s, 5,951 passed and 3 skipped (cft-fp256 19de866 docs/VALIDATION.md:26127)” on amd-arc-box (cft-fp256 19de866 docs/VALIDATION.md:26110), in the entry of 2026-10-30 (cft-fp256 19de866 docs/VALIDATION.md:26082).   3. the card: compares a device against the software backend bit for bit across the elementwise operations (cft-fp256 19de866 CONFORMANCE.md:254), which needs the FPGA and its toolchain.

VIIProve it wrong

Cheapest first; the site-wide rules of engagement are stated once, on the Corrections page.

  1. Open the web page above and hand it your own vector file: “Drop a vector file on it and it scores itself (cft-fp256 19de866 README.md:34).” Anything less than a perfect score is a disproof.
  2. make vectors locally, then compare the digests it writes with the ones the repository publishes in vectors/SHA256SUMS (cft-fp256 19de866), by the recipe CONFORMANCE.md gives; a differing line is a disproof. The record says this is a check no gate makes: “no gate compares a set's digest with vectors/SHA256SUMS (cft-fp256 19de866 CONFORMANCE.md:316).”
  3. Replay the identity protocol yourself in another language and compare its checksum line against the ones docs/COMPATIBILITY.md (cft-fp256 19de866) records; a differing hex value is a disproof.
  4. Rebuild host/tools/mpfr_check.c and widen its sweep past the campaign's own cases: the independent oracle is only as good as the cases put to it. The record names one it lacks: “The MPFR campaign's pool (host/tools/mpfr_check.c, build_tpool) lacks the tie's argument, so the gate's mpfr stage does not test the fix; XT-1's probe does (cft-fp256 19de866 docs/VALIDATION.md:18240).” The record's newest entry adds a limit of the same kind, after a case the oracle had never been asked (the entry): “the oracle is only as wide as its pools: the ten now see both, and nothing but this case moved, but no sweep has asked which families any pool lacks (cft-fp256 19de866 docs/VALIDATION.md:26224).”
