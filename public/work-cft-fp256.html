IWhat it is

A math coprocessor that gets the same answer everywhere (cft-fp256 ab51655 README.md:3). It does IEEE 754 arithmetic at four precisions - 32, 64, 128 and 256 bits - and guarantees that the same inputs give the same bits whether the work runs on a laptop CPU, in a browser tab, on a microcontroller, or on the FPGA card it was designed for (cft-fp256 ab51655 README.md:5).

IIWhat it is not

Raw fp32 and fp64 throughput (cft-fp256 ab51655 README.md:64). Every CPU and GPU on the market serves those formats at clocks and lane counts an FPGA fabric will not match, and nothing here pretends otherwise (cft-fp256 ab51655 README.md:64). The tile earns its place at the precisions commodity hardware does not offer, and on the guarantee that the answer does not move (cft-fp256 ab51655 README.md:70).

IIIThe contract

Named levels, quoted from CONFORMANCE.md: “Level A - IEEE 754-2019 in radix 2 (cft-fp256 ab51655 CONFORMANCE.md:16)” is the standard itself; “Level B - the cft-fp256 profile (cft-fp256 ab51655 CONFORMANCE.md:22)” is “Level A, plus every choice the standard leaves to the implementation fixed to one answer, plus operations the standard does not define (cft-fp256 ab51655 CONFORMANCE.md:22).” The relationship runs one way, in the document's own words: “An implementation conforming to the cft-fp256 profile conforms to (cft-fp256 ab51655 CONFORMANCE.md:27) IEEE 754-2019 in radix 2 for the operations the profile covers (cft-fp256 ab51655 CONFORMANCE.md:28).”

The README states the promise directly: “That guarantee is the product (cft-fp256 ab51655 README.md:10).” The hardware only makes it faster (cft-fp256 ab51655 README.md:10).

The contract is versioned. CONFORMANCE.md opens with its profile, “Profile 3, 2026-10-05 (cft-fp256 ab51655 CONFORMANCE.md:3)” (profile 2 was 2026-10-02 and profile 1 2026-09-16 (cft-fp256 ab51655 CONFORMANCE.md:3)), and says of the tree: “a major step: recorded bits moved (cft-fp256 ab51655 CONFORMANCE.md:334).” A major step is “a change to any recorded bit or flag, or to an accepted image's result, flags, STATUS or acceptance (cft-fp256 ab51655 CONFORMANCE.md:279).”

VKept failures

  • cocotb's inability to set an exit code — stated in its own makefile at Makefile.inc:88, which checks only that the file *exists* — meant three real RTL failures were reported as a pass (cft-fp256 ab51655 CLAUDE.md:90). Fixed by the entry 2026-09-12 - two gates that could not fail, and the path that has always been the critical one (cft-fp256 ab51655 docs/VALIDATION.md:10952), commit f192bf0 (cft-fp256 f192bf0).
  • a device predating a new capability flag ignored an unchecked reserved bit and read far past a one-element buffer (HonestFramework 65447fd CASE-STUDY.md:63: “Nothing validated the reserved bits of a control word, so a device predating a new flag ignored it and read a thousand elements from a one-element buffer”) — measured as a host-side segfault in the entry 2026-09-12 - a stride-0 operand, the MODE guard it needed, and a contract I misread (cft-fp256 ab51655 docs/VALIDATION.md:10803). Fixed by commit 8b7dea1 (cft-fp256 8b7dea1).
  • exp2 at x = emin - p (cft-fp256 ab51655 CONFORMANCE.md:336): Its exact value 2^(emin - p) is half the smallest subnormal, the tie between +0 and it, which IEEE 754's roundTiesToAway (rmm) rounds to the subnormal. The model rounded it as a quarter of the subnormal and gave +0 (cft-fp256 ab51655 CONFORMANCE.md:336). Step 6's design study M1 found it (its question 5), verifier-VM1 confirmed it (cft-fp256 ab51655 CONFORMANCE.md:344) — in the entry 2026-10-05 - the golden model's exp2 tie fixed, and the conformance profile's major step to 3 (parcel XT); M1's design study merged as a design record (cft-fp256 ab51655 docs/VALIDATION.md:18203). Fixed by commit ca43695 (cft-fp256 ca43695).

VITest it

VIIProve it wrong

Cheapest first; the site-wide rules of engagement are stated once, on the Corrections page.

  1. Open the web page above and hand it your own vector file: “Drop a vector file on it and it scores itself (cft-fp256 ab51655 README.md:34).” Anything less than a perfect score is a disproof.
  2. make vectors locally, then compare the digests it writes with the ones the repository publishes in vectors/SHA256SUMS (cft-fp256 ab51655), by the recipe CONFORMANCE.md gives; a differing line is a disproof. The record says this is a check no gate makes: “no gate compares a set's digest with vectors/SHA256SUMS (cft-fp256 ab51655 CONFORMANCE.md:312).”
  3. Replay the identity protocol yourself in another language and compare its checksum line against the ones docs/COMPATIBILITY.md (cft-fp256 ab51655) records; a differing hex value is a disproof.
  4. Rebuild host/tools/mpfr_check.c and widen its sweep past the campaign's own cases: the independent oracle is only as good as the cases put to it. The record names one it lacks: “The MPFR campaign's pool (host/tools/mpfr_check.c, build_tpool) lacks the tie's argument, so the gate's mpfr stage does not test the fix; XT-1's probe does (cft-fp256 ab51655 docs/VALIDATION.md:18237).”
