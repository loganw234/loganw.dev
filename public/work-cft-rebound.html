IWhat it is

REBOUND's IAS15 integrator with its arithmetic routed through libcft, the IEEE 754-2019 binary32/64/128/256 library of the cft-fp256 project, so that the same integrator runs at binary64, binary128 and binary256 - and, given an artifact, on the FP256 tile - with the same bits everywhere (cft-rebound 039e3c3 README.md:3).

IIWhat it is not

The README carries no “what it is not” heading. Its nearest equivalent is “Scope: what it integrates, and what it refuses (cft-rebound 039e3c3 README.md:15)”, a refusal list rather than a limits statement. In the README's own words: “Everything below is refused, by name, with a message - never silently ignored, never approximated (cft-rebound 039e3c3 README.md:42). The list is one table in code (cft_support_rows, src/cft_supported.c) that both entry points walk, and the gate walks it too and fails on any row no case exercises (cft-rebound 039e3c3 README.md:43)”

  • this is direct summation. REB_GRAVITY_COMPENSATED is refused too: a different summation from the one ported (cft-rebound 039e3c3 README.md:53)
  • WHFast is ranked first to follow (docs/INTEGRATORS.md) and has not been done (cft-rebound 039e3c3 README.md:58)
  • a heap overread in REBOUND's own gravity loop. There is no bit-identity to claim against undefined behaviour (cft-rebound 039e3c3 README.md:56)

IIIThe contract

At binary64 it is REBOUND's own IAS15 bit for bit, which is a gate the port passes on every build (cft-rebound 039e3c3 README.md:22).

VKept failures

  • REBOUND's IAS15 was thought to leave a *stale polynomial* behind when a particle is removed (cft-rebound 039e3c3 docs/VALIDATION.md:2714). So the polynomial is not stale. It is aliased, and the survivors do not inherit each other's coefficients - they inherit fragments of the level above (cft-rebound 039e3c3 docs/VALIDATION.md:2749) — 2026-09-11 (cft-rebound 039e3c3 docs/VALIDATION.md:2705), 30. Collisions, and a defect that was not the one we wrote down (cft-rebound 039e3c3 docs/VALIDATION.md:2705). Fixed by commit 1561d35 (cft-rebound 1561d35).
  • A banner is the only place in this suite that states a step count without executing it, so under --light it was the only place that could overstate the work done (cft-rebound 039e3c3 docs/VALIDATION.md:3109) — 2026-09-11 (cft-rebound 039e3c3 docs/VALIDATION.md:3070), 33. --light, and the banner that overstated it (cft-rebound 039e3c3 docs/VALIDATION.md:3070). Fixed by commit e12aed9 (cft-rebound e12aed9).

VITest it

  1. make check-quick: cheaper arguments + the gate cache (cft-rebound 039e3c3 CLAUDE.md:32), 5 s warm (cft-rebound 039e3c3 CLAUDE.md:32).
  2. make check-light: cheaper arguments, the cache, and step counts scaled down (cft-rebound 039e3c3 CLAUDE.md:33: “cheaper arguments + cache + scaled step counts”), ~9 min (cft-rebound 039e3c3 CLAUDE.md:33).
  3. make check: every gate at every format, never skipping one (cft-rebound 039e3c3 CLAUDE.md:31: “every gate at every format, never skips”), ~55–70 min (cft-rebound 039e3c3 CLAUDE.md:31).

VIIProve it wrong

Cheapest first; the site-wide rules of engagement are stated once, on the Corrections page — not yet built, so this dossier does not link it.

  1. make check-quick on a clean clone, and see whether the cache lets anything silently pass: Every skip prints itself by name (cft-rebound 039e3c3 CLAUDE.md:38).
  2. make check-light end to end, and compare it against make check on the same commit: a scaled leg that disagrees with the full one is a disproof.
  3. Point CFT_REBOUND_ARTIFACT at the software backend and at a card image on the same problem and diff every coordinate: the contract is bit identity at binary64, not agreement within a tolerance.
  4. Run make check itself, which executes (cft-rebound 039e3c3 CLAUDE.md:36), and read the log rather than the exit code.
