cft-fp256's contract, in its own words: “It is written so that an implementation can be built and proven without this repository's RTL or library - a different chip, a different process, a different language - and still be interchangeable with them bit for bit (cft-fp256 19de866 CONFORMANCE.md:9).” The checks below are how a reader confirms that directly, without taking this site's word for it.

IWays to check this

Don't trust this - run one.

  1. cft-fp256's own conformance replay, in the browser. Cost: a browser tab, nothing installed. It replays the published conformance vectors in front of you (cft-fp256 19de866 README.md:30). What it holds, in the page's own README: “The embedded sample (4,015 cases; deterministic rule below) spans all four formats, all five rounding attributes and every opcode class (cft-fp256 19de866 bindings/wasm/README.md:45).” And for the full claim: “For the full 1,072,415-case claim, generate the sets in a checkout (make vectors) and drag the vectors/out/*.jsonl files onto the page - same code path, whole files (cft-fp256 19de866 bindings/wasm/README.md:49).” What a green verdict proves, in the same README: “compiling this library to wasm cannot have changed a single result bit, and the replay shows it did not (cft-fp256 19de866 bindings/wasm/README.md:25).” Its module is a committed build product, and cft-fp256's record says of it, in the entry of 2026-10-30 (cft-fp256 19de866 docs/VALIDATION.md:26149): “the committed module was stale from 2026-10-22 (cft-fp256 19de866 docs/VALIDATION.md:26187),” and “b9d60ebc, the module. The node module, the conformance page and the demos page were rebuilt in the pinned emsdk 6.0.9 image (cft-fp256 19de866 docs/VALIDATION.md:26185).”
  2. make golden in a clone of cft-fp256. Cost: the record's newest timing of the golden stage, in the entry of 2026-10-30 (cft-fp256 19de866 docs/VALIDATION.md:26082), on amd-arc-box (cft-fp256 19de866 docs/VALIDATION.md:26110): “golden ok 3,385 s, 5,951 passed and 3 skipped (cft-fp256 19de866 docs/VALIDATION.md:26127).” The stage the runner runs for it is “PY -m pytest "$ROOT/python/tests" -q -rs --color=no (cft-fp256 19de866 verify/run.sh:639),” which names no worker option. make golden itself runs “$(PYTHON) -m pytest python/tests -q $(if $(XDIST_N),-n $(XDIST_N),) (cft-fp256 19de866 Makefile:112),” which adds pytest-xdist's workers “only if this interpreter has it (cft-fp256 19de866 Makefile:22).” So what make golden takes depends on the machine and on whether pytest-xdist is installed. The golden model's self-tests (cft-fp256 19de866 README.md:326): Its pytest suite checks the model against its own invariants and against mpmath and MPFR where they can arbitrate (cft-fp256 19de866 docs/VERIFICATION.md:37). Nothing below re-litigates a value it has decided (cft-fp256 19de866 docs/VERIFICATION.md:39).

IIWhat checking here does not do

Every quotation above is read from cft-fp256's own documents, at the commit this site pins - the same discipline this whole site holds itself to. That shows this page quotes cft-fp256 faithfully. It does not show that cft-fp256's claims are true: cft-fp256's own gates decide that, and the checks above are how a reader runs them directly, rather than taking this site's word for it. A link to one of cft-fp256's hosted pages opens whatever its host serves now, which may be a later commit than the one this site reads.

What cft-fp256's own documents say their checks do not reach:

  • “One stage in this layer holds the library to something this project did not compute (photograph): atlas-engine's deterministic camera around a plate as a sequencer program, each pass's deposit buffer held to the SHA-256 an NVIDIA GPU wrote while rendering the same frame from pinned GLSL. Every other stage here compares the C with the golden model, and a defect the two shared would pass them all; this one would not (cft-fp256 19de866 docs/VERIFICATION.md:87).” The record shows a defect of that kind: “Under rmm IEEE 754's roundTiesToAway gives sigma; transcend.exp2 gave +0 (cft-fp256 19de866 docs/VALIDATION.md:18209),” and “golden, libcft and the oracle agree at ba03b1d, and at 3a2b2d0 exactly the four rmm ties are wrong (cft-fp256 19de866 docs/VALIDATION.md:18222).” Step 6's design study M1 found it (its question 5), verifier-VM1 confirmed it (cft-fp256 19de866 CONFORMANCE.md:402), in the entry 2026-10-05 - the golden model's exp2 tie fixed, and the conformance profile's major step to 3 (parcel XT); M1's design study merged as a design record (cft-fp256 19de866 docs/VALIDATION.md:18206). A later one is in the entry of 2026-10-30 (cft-fp256 19de866 docs/VALIDATION.md:26149): “exp2m1(emax + 1) toward zero raised overflow, in the golden model, the C, the vectors and the WebAssembly module (cft-fp256 19de866 docs/VALIDATION.md:26149).” It came, in the entry's words, from “a clean-room audit of loganw234/muse-softfloat (binary16/32/64), cross-tested against this library and an exact arbiter (cft-fp256 19de866 docs/VALIDATION.md:26151).” Why no gate caught it, in the entry's words: “The vectors are the golden model's (cft-fp256 19de866 docs/VALIDATION.md:26166),” “transcend_check.py compares the C with the golden model, and the two shared the shortcut (cft-fp256 19de866 docs/VALIDATION.md:26167),” and “The MPFR oracle never asked (cft-fp256 19de866 docs/VALIDATION.md:26168).” Its own known limit: “the oracle is only as wide as its pools: the ten now see both, and nothing but this case moved, but no sweep has asked which families any pool lacks (cft-fp256 19de866 docs/VALIDATION.md:26224).”
  • “no gate compares a set's digest with vectors/SHA256SUMS (cft-fp256 19de866 CONFORMANCE.md:316).” The same passage goes on: “A change that moves a recorded bit or case - to the model and libcft together, or to the generator alone - therefore passes the gate budget at the vector sets (cft-fp256 19de866 CONFORMANCE.md:320).” “The full census's node and wasm stages replay the sets through the committed WebAssembly module too, so a change to the model and libcft fails there until the module is rebuilt with it, and then passes. From then on, and for a change to the generator alone throughout, only the comparison above shows it. It is not closed now: closing it changes verify/run.sh, which would need a gate run of its own (2026-10-05) (cft-fp256 19de866 CONFORMANCE.md:323).” The entry of 2026-10-22 (cft-fp256 19de866 docs/VALIDATION.md:23474) agrees: “no gate compares a regenerated set's digest with the tracked record (cft-fp256 19de866 docs/VALIDATION.md:23511).”
