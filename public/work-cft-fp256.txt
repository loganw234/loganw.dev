cft-fp256 — dossier
===================

I. What it is

A math coprocessor that gets the same answer everywhere [fact 1987]. It does IEEE 754 arithmetic at four precisions - 32, 64, 128 and 256 bits - and guarantees that the same inputs give the same bits whether the work runs on a laptop CPU, in a browser tab, on a microcontroller, or on the FPGA card it was designed for [fact 1988].

II. What it is not

Raw fp32 and fp64 throughput [fact 1989]. Every CPU and GPU on the market serves those formats at clocks and lane counts an FPGA fabric will not match, and nothing here pretends otherwise [fact 1990]. The tile earns its place at the precisions commodity hardware does not offer, and on the guarantee that the answer does not move [fact 1991].

III. The contract

Named levels, quoted from CONFORMANCE.md: “Level A - IEEE 754-2019 in radix 2 [fact 1992]” is the standard itself; “Level B - the cft-fp256 profile [fact 1993]” is “Level A, plus every choice the standard leaves to the implementation fixed to one answer, plus operations the standard does not define [fact 1994].” The relationship runs one way, in the document's own words: “An implementation conforming to the cft-fp256 profile conforms to [fact 1995] IEEE 754-2019 in radix 2 for the operations the profile covers [fact 1996].”

The README states the promise directly: “That guarantee is the product [fact 1997].” The hardware only makes it faster [fact 1998].

The contract is versioned. CONFORMANCE.md opens with its profile, “Profile 3.1, 2026-10-13 [fact 1999]” (profile 3 was 2026-10-05, profile 2 2026-10-02 and profile 1 2026-09-16 [fact 2000]), and says of the tree: “a minor step: cases added, none moved [fact 2001].” A minor step is “an addition that changes no recorded case and no accepted image [fact 2002].”

What CONFORMANCE.md says of the tree, “a minor step: cases added, none moved [fact 2003],” is that document's own word as of its last change, 2026-10-15 [fact 2004]. The ledger's newest entry, of 2026-10-30 [fact 2005], reports a fix that changed published records: “The 8 that change are the rtz and rdn transcendental sets of each format, each by exactly one record, exp2m1(emax + 1): the same value, flags 20 to 16. The unfixed model's 72 rtz and rdn sets equal the committed record, so those 8 records are the published ones moving [fact 2006].” The same document calls a change to any recorded bit or flag a major step: “a change to any recorded bit or flag, or to an accepted image's result, flags, STATUS or acceptance [fact 2007].” The pin holds both.

V. Kept failures

- cocotb's inability to set an exit code — stated in its own makefile at Makefile.inc:88, which checks only that the file *exists* — meant three real RTL failures were reported as a pass [fact 2037]. Fixed by the entry 2026-09-12 - two gates that could not fail, and the path that has always been the critical one [fact 2038], commit f192bf0 [fact 2039].
- exp2 at x = emin - p [fact 2040]: Its exact value 2^(emin - p) is half the smallest subnormal, the tie between +0 and it, which IEEE 754's roundTiesToAway (rmm) rounds to the subnormal. The model rounded it as a quarter of the subnormal and gave +0 [fact 2041]. Step 6's design study M1 found it (its question 5), verifier-VM1 confirmed it [fact 2042] — in the entry 2026-10-05 - the golden model's exp2 tie fixed, and the conformance profile's major step to 3 (parcel XT); M1's design study merged as a design record [fact 2043]. Fixed by commit ca43695 [fact 2044].
- At x = emax + 1, under roundTowardZero and roundTowardNegative, exp2m1 returned the largest finite, which is right, with overflow | inexact (0x14), which is wrong [fact 2045]. Reported, in the entry's words, “from a clean-room audit of loganw234/muse-softfloat (binary16/32/64), cross-tested against this library and an exact arbiter [fact 2046]” — in the entry of 2026-10-30 [fact 2047]. No gate had caught it: “The MPFR oracle never asked [fact 2048].” Fixed by commit 48e2aa22 [fact 2049].

VII. Prove it wrong

Cheapest first; the site-wide rules of engagement are stated once, on the Corrections page.

- Open the web page above and hand it your own vector file: “Drop a vector file on it and it scores itself [fact 2060].” Anything less than a perfect score is a disproof.
- make vectors locally, then compare the digests it writes with the ones the repository publishes in vectors/SHA256SUMS [fact 2061], by the recipe CONFORMANCE.md gives; a differing line is a disproof. The record says this is a check no gate makes: “no gate compares a set's digest with vectors/SHA256SUMS [fact 2062].”
- Replay the identity protocol yourself in another language and compare its checksum line against the ones docs/COMPATIBILITY.md [fact 2063] records; a differing hex value is a disproof.
- Rebuild host/tools/mpfr_check.c and widen its sweep past the campaign's own cases: the independent oracle is only as good as the cases put to it. The record names one it lacks: “The MPFR campaign's pool (host/tools/mpfr_check.c, build_tpool) lacks the tie's argument, so the gate's mpfr stage does not test the fix; XT-1's probe does [fact 2064].” The record's newest entry adds a limit of the same kind, after a case the oracle had never been asked (the entry): “the oracle is only as wide as its pools: the ten now see both, and nothing but this case moved, but no sweep has asked which families any pool lacks [fact 2065].”
